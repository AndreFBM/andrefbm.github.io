From messy partner data to shipped software.

I'm a Data Engineer at Ask-to-Print, a web-to-print company where every order travels through a network of suppliers and production partners. My job is to make that network run on data: integrations, pipelines, internal APIs and the tools partners use every day.

This year the work grew from scripts into products: a desktop app, an internal API, test suites that try to break things. The job is still the full picture: how data gets in, how it's checked, and whether the output is actually right.

// how I work

Write it down.
Ship it small.

My bigger builds start as a written spec, not a script, and every trade-off ends up somewhere I can point to. Boring releases are the goal.

  1. 01

    Spec it

    Context, stack and non-negotiables, written down first. The partner app's brief was a 21 kB document before a single line of code existed.

  2. 02

    Ship small

    Small, versioned increments with modern tooling, AI-assisted where it helps: v0.1.0 to v0.1.13 so far.

  3. 03

    Decide on paper

    Every trade-off lands in a decision log. If I can't explain it, it doesn't ship.

  4. 04

    Verify

    Tests, strict typing, linting, the API contract and light/dark screenshots gate every release.

## v0.1.6 — Box permissions per partner

One can_edit_boxes flag controls quantity, weight and dimensions. Admin-only, every change audited.

The server re-validates every box atomically before creating a shipment, including requests from old or tampered clients.

Restricted clients hide editing and never send locally changed values.

A permission refusal removes only the rejected local operation, then reloads the list.
